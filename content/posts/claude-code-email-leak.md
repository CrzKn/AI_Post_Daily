你让跑腿的人去便利店问一句「还有没有牛奶」。对方进门先递上你的身份证复印件：「我替这位用户来问的。」店员没多问，把复印件和问题一起记进了本子。

听起来荒谬，但类似的事正在发生：有人在 Claude Code 的仓库里提了个 issue，说这个命令行 agent（能自己调用工具、连续跑多步任务的程序）在帮用户读网页时，请求里夹带了账号关联的邮箱。

目标网站什么都不用做。它照常记访问日志——来源 IP、客户端标识、时间戳——只是这次多了一行邮箱。翻日志的人立刻能对上号：哦，是这个人在用 agent 读我们的页面。

「被动」两个字是关键。网站不需要植入追踪脚本，不需要 Cookie，不需要破解什么；只要日志开着，你就被登记了。而你这边毫无感知。

## 一、问题不在模型，在请求

很多人第一反应是「模型又乱说话了」。这次不是。agent 读网页，本质上就是替你发一次 HTTP 请求。请求除了网址，还会带上一串附加信息：什么客户端、什么版本、以谁的身份。邮箱就藏在这串信息里。

这类字段本来是给服务端用的：限流、统计、排查故障。可一旦它指向一个真实的人，性质就变了——从「某客户端在访问」变成「某个人在访问」。而 agent 跑一次任务，可能连读十几个陌生站点。

从 issue 描述看，这更像工程实现里顺手带上的字段，而非有意设计来收集数据。但正是「顺手」，暴露了默认值没人认真讨论过。更麻烦的是，用户通常看不到这层信息：它不在聊天窗口里，也不在输出里，只存在于网络请求中。

## 二、给的理由，不算离谱

支持这种做法的人，理由大体落在「配额」和「溯源」上。额度要挂在账号上：免费次数、调用频率总得有个计数对象，邮箱是最现成的账号主键。溯源则是为了防滥用：有人拿 agent 刷站、爬数据，服务端得能顺着身份找到人。还有一层现实考虑：用户报「我这边一直失败」时，按身份对日志最快。

打个比方，这像健身房进门刷卡。前台知道你是谁，也方便统计客流。问题在于，健身房只有一家，而 agent 一次出门要进十几家店，每家都拿到同一张卡。

## 三、邮箱为什么特殊

它不是随机生成的 ID，而是跨站点通用的主键。你在 A 站留的邮箱、在 B 站留的邮箱，是同一个字符串；把两份日志并排一放，就是一张行为地图：这个人在查什么资料、多久查一次、对什么话题感兴趣。

后果可以拆成三层。最轻的是画像与定向：知道你在用 agent 批量读竞品文档，就可以给你看不同的价格、不同的广告。往上一层是骚扰与滥用：邮箱进了名单，垃圾邮件、钓鱼、撞库（拿泄露的邮箱密码去试别的站点）接踵而来。最重的是身份串联：邮箱往往还绑着社交、支付、云服务账号，一次暴露的连锁损失，远大于一个随机 ID。

还有一层不容易说清的影响：心理上的。你以为自己在「随便看看」，其实每次访问都带着名字。agent 把浏览变快了，也把实名变成了默认设置。

## 四、配额要的是钥匙，不是名字

讨论里有个细节值得单独拎出来：站点真正需要知道的，是「这把钥匙今天用了几次」，而不是「钥匙属于谁」。这两件事可以拆开。

酒店房卡就是现成的例子：门锁认卡，前台知道房号，但走廊监控不必记录你的身份证号。工程上并不缺办法：一次性 token、按会话计数、本地代理转发、站点只存聚合数据。这些方案不新，难的是默认值怎么定。

现在的默认值偏向「带上」，让每个收到请求的站点自己决定存不存；更稳妥的默认是「不带」，确实需要溯源的场景再显式授权。这不是技术难题，是产品取舍：优先方便排查，还是优先保护使用者。

值得追问的还有一点：谁能改这个默认值。用户改不了，因为请求是工具发出的；站点也改不了，因为它只是被动接收。能做决定的，只有写 harness（包在模型外面、替你跑命令读文件的那层工具）的人。

## 五、普通用户可以做什么

门槛最低的一条：别用主邮箱登录这类工具。给 agent 配一个专用别名邮箱，真出事时损失可控。

第二条：关心它出门带了什么。有的工具会提供调试日志，能看到完整的出站请求；没有这类开关的，至少要知道「它在替我实名访问」这件事存在。

第三条：收窄活动范围。别让 agent 拿着你的身份去访问公司内网、付费内容、个人后台——这些地方的日志比公开网站更细。如果团队在批量使用这类工具，最好把这些约定写进规范：哪些域名允许访问、用哪个账号、日志留多久。

第四条：把它当成选型指标。和上下文管理、失败重试一样，出站请求带不带身份，也是 harness 的一部分；只不过前面几项影响体验，这一项影响安全。

## 结尾：它口袋里装了什么

回到开头那个跑腿的人。替你办事，出示证件可以是礼貌；但出示哪张证件、给谁看、看多久，应该由你决定。agent 的便利，建立在「替你做主」之上；身份这件事，恰恰不能替你做主。

下次让 agent 出门前，值得先问一句：它口袋里装了什么？
