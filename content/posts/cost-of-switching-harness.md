把 Claude Code 换成另一个开源 agent，听上去跟「换个 App」差不多轻：卸掉旧的、装上新的，命令行里敲一行就行。可真有人动手时才发现，要搬的根本不是那个负责思考的大脑。真正要搬的，是长在大脑外面的一圈东西——自己攒的脚本、用惯的斜杠命令、挂在各处的 hooks，一样不剩，全得推倒重写。这件事把一个问题顶到了明面上：为什么换个模型只要改一行配置，换个「壳」却要伤筋动骨？

## 一个真实的迁移案例

这位开发者选中的新壳叫 Pi，一个开源的命令行 agent。他换过去的理由和性能无关：Claude Code 已经够强，问题出在成本与掌控感。Pi 允许他随时切换底层模型，今天接这个、明天接那个，不必被绑死在一家；上下文到底怎么拼装，他能看得一清二楚，不再是一团黑箱；出了 bug 也能自己动手改，不用等官方发版。

代价同样具体——原来那套围绕 Claude Code 长出来的工作流，脚本、斜杠命令、hooks，必须一样不剩地重写。迁移的真实账单，落在了工具链，而不是模型。

这里藏着一个反直觉的地方：「可换模型」既是吸引人的卖点，也是一份看不见的工作。换模型的自由，意味着换壳、换上下文、换出错兜底的责任，全都落到了你自己头上。少了平台的包办，就多了自己的维护。

## 先把两个词拆开

要算清这笔账，得先把两个总被人混用的词分开：agent 和 harness。

agent 是三样东西的组合：一个模型、一层循环、一套工具调用。它是一个会想、会做、还会反复干活的执行体。

harness 是外面那层脚手架：上下文要如何裁剪、工具要如何注册并鉴权、失败要如何重试、结果要如何评测。

一句话概括：agent 负责「想和做」，harness 负责「把想和做框起来、管起来、兜住底」。

这两者常被捆在一起谈，因为市面上的「编码助手」大多把 agent 和 harness 打包成一个产品卖。可只有拆开看，你才明白自己到底换掉了哪一半。

## 成本为什么总落在工具链上

模型是个能被一行配置换掉的零件，harness 是长在它周围的习惯。你在一个工具上待得越久，往里面投的越不是「模型」，而是脚本、权限、重试策略、评测口径——这些东西都不长在模型上，全挂在脚手架里。所以换工具的账单，从来不是「换个模型」，而是「把这些长在外壳上的东西，重新种一遍」。

打个比方，模型像发动机，harness 像整套车身。发动机可以整体抬出来，一小时换一台新的；可方向盘、刹车、仪表盘都焊在车架上，想换它们，等于重新造一辆车。你攒下的脚本和 hooks，就是焊在车架上的那部分。这也解释了为什么「换个更强的模型」很少能直接换来「更好用」——上限被抬高了，可你日常体验的绝大部分，其实是由脚手架决定的。

## 四个模块，各要重做什么

把 harness 拆成四个可测的模块，迁移要改什么就一目了然。

一是上下文拼装：历史消息怎么裁剪、长对话怎么摘要、系统提示怎么排序，每个工具各有各的做法，换壳等于重学一遍。

二是工具边界与鉴权：允许模型碰哪些命令、能读哪些文件、什么操作要二次确认。这张权限网要重新织，织松了会闯祸，织紧了又干不了活。

三是失败重试：哪类错误该重试、退避多久、什么情况该停下等人，策略得重新调。不同工具对「失败」的定义都不一样。

四是评测口径：一套任务跑完算不算「完成」，用通过率还是用可复现的测试集，标准也得重新定。这是四块里最难的一块——没有统一的尺子，就不知道新壳到底比旧壳强在哪。

下面这段最小可跑的代码，把这四个模块放在了一起：

```python
def call_model(prompt: str) -> str:
    """演示用假模型：任务需要工具时返回工具调用，否则直接回答。"""
    if "需要工具" in prompt:
        return "TOOL:search"
    return "这是答案"


def run_tool(name: str) -> str:
    """工具边界：只放行白名单里的工具。"""
    whitelist = {"search": "检索结果"}
    return whitelist.get(name, "")


def trim_context(task: str) -> str:
    """上下文裁剪：只留当前任务，窗口外的历史不塞进来。"""
    return f"任务：{task}"[:2000]


def harness(task: str):
    """最小 harness：裁剪 -> 调用 -> 工具 -> 重试 -> 评测。"""
    prompt = trim_context(task)
    for _ in range(3):                    # 失败重试：最多 3 次
        out = call_model(prompt)
        if out.startswith("TOOL:"):       # 工具注册与鉴权
            out = run_tool(out.split(":", 1)[1])
        if out:                           # 结果评测：非空即通过
            return out
    return ""


assert harness("需要工具的活儿") == "检索结果"
assert harness("普通提问") == "这是答案"
print("harness 四模块演示通过")
```

## 模型是上限，harness 决定你离上限多近

社区那场讨论得出的结论很直接：把同一个模型装进两套不同的 harness，跑同一批任务，完成率能拉开一大截。这句话背后的意思是，模型只决定天花板，harness 决定你实际能摸到多高。决定一个 agent 能不能进生产的，往往不是那个最强的模型，而是脚手架把它伺候得好不好。

下次你想换工具的时候，不妨先回头看看自己的脚本、命令和 hooks 长了多少。那才是你真正的迁移成本，也是你最该握在自己手里的东西——因为模型可以一键换，脚手架却只能重头搭。换壳从来不是一件小事，它换掉的是你日复一日攒下来的那些习惯。说到底，模型是租来的，harness 是自己攒的；租来的随时能换，攒下的才最贵。
