同样一份手机套餐，两个人到月底的账单可以差出一倍。一个整天连着 Wi-Fi，流量几乎没动；另一个常年在路上，流量包早早见底，还要为超出的每一兆单独付钱。价目表长得一模一样，账单却像两份合同。

最近 DeepSeek 把聊天、推理、写代码这几样本事收进同一个 API 入口，对外统一计费，每个 token 的单价延续它一贯的亲民路线。消息一出，开发者群里吵的不是能力好不好用，而是那句老话：这个价格，你接不接受？因为低价这件事，单独看毫无意义，放进自己的业务里才作数。

有意思的是，两边的理由都不在单价上。一派认为，重点从来不是标价，而是配额与稳定性——单价再低，高峰期拿不到额度，生产环境照样瘫掉。另一派算得更细：低价背后靠的是 cache 命中率和 batch 排队，一旦上下文拉长，实际花的钱往往高出标价。

这两句听上去各说各的，其实指向同一件事：价目表只是菜单，账单由别的东西决定。

## 同一个单价，三种账单

把一张 API 账单拆开，同一个 token 单价，最后落在三个变量上：cache 命中、batch 排队、用量形状。

**cache 命中：一壶水是煮一次，还是煮十次。** 很多应用每次请求都带一大段几乎相同的系统提示和背景说明。服务商可以只算一次，后续请求复用同一段前缀，命中率越高，真实单价越贴着标价走。反过来，如果业务里每个请求的前缀都是新的，缓存帮不上忙，账单就往上抬。好比烧水：煮一壶全家喝，和每隔十分钟重新煮一壶，燃气表走得完全不同。

**batch 排队：你的请求能不能等。** 服务商靠批处理摊薄推理成本，前提是请求愿意排队。离线跑批、夜里生成、异步任务，这类活儿可以攒成一摞再处理，相当于峰谷电价里把洗衣机调到半夜——电没变，价格是另一档。可在线对话、实时交互一分钟都等不了，只能挤「尖峰」通道，成本自然更高。

**用量形状：自助餐的标价，是按平均食量定的。** 低价通常预设了一个「平均用户」：前缀复用不错、请求能排队、上下文长度正常。如果你恰好是长上下文、高并发、还要低延迟的那一类，你就不在平均线上。自助餐按平均食量定价，遇到大胃王，餐厅的账就是另一本；你的用量形状偏离平均越远，实际单价离标价越远。

这三项还不是孤立的。cache 命中差的业务，通常对延迟也敏感，于是又吃不到 batch 的红利，两项劣势叠在一起，账单就比标价难看许多。反过来，能接受异步的离线业务，往往也能把前缀设计得高度复用，等于同时赚到两档优惠。

## 单价之外，还有第二张账单

就算把上面三项都算清楚，账单还藏着一行更贵的东西：容量。

讨论里反复出现的那句话，值得再读一遍——价格再低，高峰期拿不到额度，生产环境就用不了。它点破的是：API 买的不只是「每个 token 多少钱」，还有「关键时刻你能拿到多少」。前者印在价目表上，后者写在服务商的容量安排里，而容量安排从不贴成一张漂亮的价格页。容量也不是平均分配的，它偏向那些用量平稳、可预测的客户，而不是单价谈得最低的客户。

拿健身房会员卡打比方最直观。月费便宜到心动，可你每天下班过去，器械永远满员，这张卡的真实成本就是「月费加上你永远排不上的那一个小时」。生产环境更残酷：用户不会因为你的供应商便宜，就原谅你的服务在晚高峰转圈。p99 延迟、配额、稳定性这些词，从不出现在单价里，却会在出事当天变成最贵的一行。

所以「低价」和「便宜」是两回事。低价是价目表上的事实；便宜是你的用量形状撞上对方的容量安排之后，算出来的结果。

## 选 API，不是比价目表

既然账单由用量形状和容量安排共同决定，选 API 的姿势也就反过来了：先量自己，再问对方，最后算自己的账。

先量自己。把最近一个月的请求日志翻出来，看三件事：可复用的前缀占比有多高、多少请求能容忍排队、峰值和谷值的落差有多大。这三项决定你吃 cache 和 batch 红利的能力。不用精确到个位数，先分清自己更像哪一头，比盲目比价有用得多。

再问对方。别只问「一个 token 多少钱」，还要问：高并发下的额度怎么给、稳定性有什么承诺、超长上下文有没有额外的计价规则。对方答得越含糊，第二张账单的风险就越大。

最后算自己的账。把你自己的用量形状代进去算，而不是拿对方示例里的场景代进去。示例永远挑最漂亮的角度，你的业务不会。

回到开头那个问题：DeepSeek 全家桶的价格，你接不接受？这个问题没有标准答案——或者说，答案根本不在价目表上。真正该问的是另一句：我的用量形状，撞上你的容量安排，账单会长成什么样？把这一句算清楚，接不接受，自然有数。这笔账不算，任何价格都可以显得便宜；算过之后，很多便宜会露出真面目。
