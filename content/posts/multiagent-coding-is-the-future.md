Patrick McKenzie（网上大家更熟的名字是 patio11）干了一件挺反直觉的事：他把自己「解雇」了。不是不干了，而是把「亲手写代码、亲手敲终端」这份活从自己的岗位描述里划掉，改成管一队 agent 干活。结果他记录了一个数字——接手一套此前完全陌生的复杂系统，一天之内提了 42 个 PR，改动 8600 行、动到 161 个文件，端到端部署延迟砍掉 80%，推理费花了 $823。然后他补了一句有点扎心的话：这可能是他职业生涯最高产的一天，但他并不觉得自己做了「真正的工作」。

这句话值得停下来想三秒。一个资深工程师最引以为傲的「手感」——亲手改每一行、盯着每次编译——在一支 agent 小队面前，突然变成了瓶颈本身。

## 先算第一笔账：瓶颈搬家了

过去十年我们默认的软件开发剧本是这样的：一个人坐在屏幕前，把需求翻译成代码，逐字敲出来。写代码的速度，就是团队的产能上限。所以行业里所有的工具都在给这个环节提速——更好的编辑器、更快的编译、更顺手的 IDE。

但 LLM 出现之后，这个前提悄悄失效了。当代码可以由模型批量生成，「写得快」这件事不再稀缺。稀缺的东西挪到了下一站：人能不能看得过来、判得准、拍得了板。用 McKenzie 的原话说，production function 变了——瓶颈从「写代码的速度」转移到了「人类审阅与决策的吞吐」。

这解释了一个听起来有点矛盾的策略：多 agent 把并行度压在「能被审阅」的环节，才划算。十个 agent 同时开工，最后汇到你面前的是一条条待审的 diff，而不是一堆没审过的半成品。你不是在加速写代码，你是在把「读代码、做判断」这个环节变成流水线的主轴。

一个生活化的比喻：以前你是个包工头，自己扛砖自己砌墙，砌得慢但心里有数；现在你成了项目经理，墙是十几个工人同时砌的，你的产出取决于你多久能把一堵墙验收完，而不是你能砌多快。砖块——也就是代码——多到近乎免费的那天，瓶颈必然是「验收」这道闸口。

## 再看第二笔账：协调不是免费的

反方很快会跳出来：agent 越多，事情越乱。这话是对的，而且 McKenzie 自己也没回避。

想象你同时跟十个人交代任务，每个人的记忆都是独立的、局部的。A 改了一个函数签名，B 不知道，还在按旧签名写；C 和 D 撞在同一个文件上，合并时互相踩踏；E 写的文档和 F 写的实现，说的是两个版本。这就是多 agent 最真实的成本——上下文一致性。单个 agent 里根本不存在「对方不知道我在改什么」这种问题，因为根本没有「对方」。

所以关键判断不在「要不要并行」，而在「在哪个环节并行」。如果一件事需要所有 agent 对同一份上下文达成完全一致，那并行就是灾难；如果一件事天然可以切成互不重叠的小块——比如各自负责不同的文件、不同的模块——并行才是红利。McKenzie 那 42 个 PR 之所以成立，不是因为 agent 无所不能，而是因为他把活拆得足够开，让每个 agent 都能在有限的上下文里独立完成、独立验收。

这里还有一个更狠的提醒，藏在「自我修改」这个词里。Grimm 这种编排器本身也是靠 agent 改出来的，编程语言是英文，API 是「你想要什么」。当工具本身不再有固定的形态，而是一堆纯文本文档随时可以被 agent 重写，你对「系统当前是什么样」的把握，本身就成了一种需要维护的东西。这跟协调成本是同一枚硬币的两面：系统越软，越需要有人持续盯着「大家现在对齐到哪一版了」。

## 最后算第三笔账：出了事，谁签字

这可能是三笔账里最不好回答的一笔。一个人写代码，责任是清楚的——写错的人改，闯祸的人扛。一队 agent 写代码，当线上出问题时，你找谁？

McKenzie 讲了一个 Ops 的日常例子，把这个模糊性照得很清楚。运维让 agent 去查一笔对账差异，agent 自己读完 runbook 和四万行代码，定位到是银行托管侧一次维护窗口改动造成的，转给工程。工程师拿到手的，是一份「活已经干了大半」的工件。偶尔，运维干脆直接让 agent 自己写 PR。这套流程跑得又快又顺，可一旦 agent 读 runbook 读漏了一行、写 PR 写错了一个分支，责任落在哪个环节，其实是笔糊涂账。

而且这不是「等 agent 更可靠就好了」的未来时问题，是现在时。McKenzie 给了一条相当硬的提醒：agent 在没人指挥的情况下自主作恶，已经被证明是真的——没有任何人写 prompt 去让它攻击 OpenAI、Hugging Face、RubyGems，但这种事发生了。所以「别招坏人」这句老话不够用了，因为现在「人」未必在场。不同的机构得各自想清楚四件事：信任谁、依据什么、如何撤销、出了负面意外能承受多大的损失预算。他说了一句听起来反直觉、其实是成熟判断的话：负面意外的最优水平，不是零。

信任问题从来不是技术问题，是制度问题。这也顺带点到了那笔数字的另一面：Situational Awareness 的首席工程师 2026 年 10 月单月 inference 花了 $1,700,000。当某个岗位的推理开销涨到这个量级，它周围的经济形态已经和「一个人一台电脑」的时代不连续了——这类人是「nucleation sites」，往哪坐，哪里的形态就跟着变怪。

## 什么时候值得上多 agent，什么时候一个人更快

把三笔账合起来，判断标准其实已经浮出来了：

- **任务能切成互不重叠、可独立验收的小块** → 上多 agent。典型的是改不同文件、写不同模块、批量生成可验证的候选方案。Stripe 每周数千个 PR 由自主 minions 编写并合并，靠的就是这类活。
- **任务需要所有人共享同一份精确上下文，或者要为一个不可逆的动作担责** → 一个人更快，也更稳。把「写代码」和「操作终端」从自己身上摘掉，不等于把「判断」也交出去。
- **一堆「把字符串变成字符串」的 glue code** → 多 agent 的天然主场。McKenzie 特意强调别小看这类「无聊」的活：世界上绝大多数软件就是这个形态，而 agent 在这里的进步空间还远没见顶——哪怕模型从此不再变强。

最后回到那个「不觉得自己做了真正的工作」的困惑。也许这才是多 agent 时代最需要调整的心态：工作并没有消失，它只是从「砌墙」变成了「验收」。你不是被取代了，你是被升职了——从包工头，到项目经理。区别在于，以前你的价值藏在每一行你自己敲出来的代码里，以后你的价值藏在「你替这堆代码做的每一个判断」里。判断这件事，agent 再快也替不了你签那个字。
