同样的发动机，装进不同的车身，圈速可以差出一个组别；同样的模型，套进不同的外壳，分数也能差出一代。今天的题目不聊「哪个模型更强」，聊的是那个越来越重要的壳。

先给 harness 一个中文解释：它是把模型包起来的运行外壳，负责把任务拆开喂给模型、决定上下文怎么裁、工具输出怎么截、失败之后要不要重来。两条新素材从不同方向指向同一件事：最终分数里，外壳的分量正在压过模型本身。它之所以容易被低估，是因为我们平时只看到榜单上的总分，看不到分数背后的外壳配置——就像只看了餐厅评分，没看后厨用的是哪套流程。

## 换壳的差距，比换模型还大

FrontierHarness Eval v1.1 做了一次直白的对照：把几款前沿模型各自接进不同的主流 harness，去完成同一组编码任务，只看通过率和成本。结果让人意外——同一个模型换一副壳，两项指标都会系统性变化。决定变化的，全是些不起眼的工程细节：上下文裁到哪一刀、工具返回的内容留多少、失败后重试还是绕行。同样一段报错信息，一个外壳原样转给模型，另一个先截成半行，模型判断错误原因的能力就完全不同。

最刺眼的是量级：某些组合之间的差距，比前后两代模型的代差还大。换句话说，砸钱升级一次模型，可能还抵不过把外壳调对。讨论里还有一个反问更值得记下：有人担心，榜单只要公开，厂商就会照着 harness 的方向去调优，这类评测的保鲜期也许只剩几个月。分数从此不是模型的成绩单，而是「模型乘以外壳」的组合成绩，甚至可能是「针对榜单调过参的组合」的成绩。

## 写完代码之后，才是关键

Claude Code 团队谈验证时，把注意力放在一个容易被跳过的位置：agent 生成完代码之后，谁来证明它真的对。他们给的做法很朴素：让 agent 亲自跑测试、亲自读输出；改之前和改之后各跑一遍做对照；人的时间只花在机器判不了的语义问题上，而不是一行行读 diff。逐行读 diff，等于人替模型做它本该做的检查——读得慢，还容易漏。

背后的判断更值得写下来：agent 能长多高，取决于它能拿到的反馈有多好。与其让代码生成得更快，不如让错误暴露得更早。生成快而错得多，只是在更快地制造返工；反馈及时而具体，模型才有机会自己把坑填上。

## 五个值得动手的工程旋钮

两条素材合起来，能拧出五个值得重审的工程旋钮，每个的默认值都该问一句为什么。

**上下文怎么裁。** 默认做法往往是贴着 token 上限一刀切：旧对话整段丢掉，任务要求、中间结论跟着一起消失。裁晚了上下文爆掉，裁早了关键约束先没。模型没有变笨，是它根本没看见该看的东西。

**工具输出怎么截。** 截得太狠，agent 看不到报错细节，只能靠猜；留得太多，噪音又把有限的上下文挤满。留多少不是小事，它是一道信息取舍题。这个旋钮本质上在决定「模型能看见什么证据」。

**失败之后怎么办。** 原样重试是花钱重复同一个错误，换条路重试才可能改变结果。把重试当成默认动作，等于默认把成本往上推。重试策略同时影响通过率和账单，却很少被单独拎出来调。

**任务拆多细。** 拆得太碎，模型丢掉全局；拆得太粗，一步走错全部重来。脚本级小活和仓库级重构的合理粒度完全不同。合适的粒度该跟着任务类型走，而不是跟着模板走。

**验证闭环怎么搭。** 这是 Claude Code 那条素材的落点：让模型自己读测试输出，改动前后做对照，人只审机器判不了的语义决策。没有这一步，前面四个旋钮都是盲拧。反馈质量的上限，就是 agent 能力的上限。

## 排行榜还剩多少信息量

如果换个外壳就能差出两代模型的差距，那么公开榜单上的那个总分，测的其实是「某个模型加上某个外壳再加上某种调优」的组合，而不是模型裸分。对采购决策来说，这个数字的信息量在缩水：你买不到榜单上那套组合，你只能买回模型，然后自己配外壳。榜单数字仍然有用，但它的口径和保质期都需要打个问号。

排行榜没有作废，只是用法变了：它适合做初筛清单，不适合做最终依据。采购团队真正缺的，是一份跑在自己任务上的对照表。真正该问的不是「哪个模型最强」，而是「哪个模型配上我自己的外壳，在我的任务上最稳」。

## 结论：建自己的评测集

对企业来说，答案很朴素：拿自己业务的真实任务和历史翻车记录，搭一套内部评测集。把过去出过事的场景固化下来，配好日常使用的 harness，跑通过率、算成本，也看错误是怎么发生的。这套东西不贵，贵的是坚持把每次翻车都记下来。失败案例尤其值钱——它记录的是模型在哪个环节、以什么姿势翻车，这比一个总分更能决定该不该上生产。

模型依然重要，它划定了上限；但外壳和验证决定你离上限还有多远。排行榜告诉你谁离上限近，自家评测集告诉你谁在及格线上。下次看榜，先别急着比数字，先问一句：这是谁的外壳，跑的是谁的任务。
